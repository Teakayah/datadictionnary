## 2024-07-13 - Python Module Docstring and Future Imports
**Learning:** In Python, the module-level docstring must always be the very first statement in a file. Placing `from __future__ import annotations` or other `__future__` imports before the docstring converts the intended docstring into a regular string expression. This causes all subsequent imports to fail Ruff's `E402` (Module level import not at top of file) check because Ruff considers the string expression as executable code preceding the imports.
**Action:** Always ensure the precise order: 1) Module docstring, 2) `__future__` imports, 3) Standard imports. When adding docstrings to files, verify that `__future__` imports are correctly positioned below the new docstring.
## 2024-08-17 - Module Docstring Position
**Learning:** In Python files, module-level docstrings (`"""..."""`) must be placed as the absolute first statement in the file, preceding all imports (including `from __future__ import annotations`). Placing imports before the module docstring demotes it to a regular string expression and triggers Ruff `E402` (Module level import not at top of file) errors.
**Action:** Ensure the module docstring is always the first statement in a file when creating or refactoring files.
## 2024-08-30 - Google Docstring Styling Programmatic Updates
**Learning:** When modifying large multiline string blocks like Python docstrings where standard unified `patch` tools frequently fail due to indentation, context, or whitespace mismatches, using a `python -c` script reading the file and using `.replace()` to safely modify the exact text block programmatically is an effective and robust workaround.
**Action:** Always prefer using inline Python `.replace()` scripts in `run_in_bash_session` to rewrite or append documentation in Python files if standard patching is rejected.

## 2024-11-20 - Documenting Databricks Connection Strategy
**Learning:** The application uses short-lived, per-query Databricks SQL Warehouse connections rather than a global connection pool to avoid "connection closed" errors caused by server-side scaling and timeouts. This crucial architectural decision was undocumented, making it unclear why a seemingly inefficient per-query connection model was chosen over standard pooling techniques.
**Action:** Ensure that connection handling logic, particularly workarounds for cloud warehouse limitations (like avoiding connection pooling due to timeouts), is explicitly documented with a "WHY IT EXISTS" section so future contributors understand the architectural constraint.
## 2024-11-20 - Documenting DuckDB Array Type Matching
**Learning:** DuckDB vector similarity search functions like `array_cosine_similarity` require both array inputs to have the exact same dimension type (e.g. `FLOAT[384]`). When vectors can vary in length based on dynamic environment configurations (like switching between mock dimensions and real Databricks embeddings), the length must be dynamically injected into a SQL typecast string to prevent type mismatch errors. This typecasting logic (`?::FLOAT[{len(vector)}]`) appears confusing ("magic") to developers unfamiliar with DuckDB's strict dimension type matching.
**Action:** Always provide "WHY IT EXISTS" context comments above dynamic SQL typecasting logic (especially involving DuckDB vector arrays) so future developers understand the underlying database constraint driving the string formatting.
