## 2026-05-04 - [Replace :latest tags with Dynamic SHA Tags using envsubst]
**Cluster Quirk:** Applying the same image `:latest` tag means nodes don't pull the newest image unless `imagePullPolicy: Always` is set. However, setting `imagePullPolicy: Always` in production causes inefficient pulling, increased startup latency, and risk of rate-limiting, and relies on mutable tags which breaks declarative deployments. The CI/CD substitution only handled `deployment.yaml` and missed `cronjob.yaml`.
**Learning:** Using `sed` targeting a specific file and regex is fragile and prone to missing resources like CronJobs or StatefulSets that also need the pinned image. `envsubst` applied across all manifests is a much more robust approach for injecting deployment variables.
**Resilience:** Replaced `:latest` with `${IMAGE_TAG}` and changed `imagePullPolicy` to `IfNotPresent` in both `deployment.yaml` and `cronjob.yaml`. Replaced `sed` with an `envsubst` loop in the GitHub Action to ensure all resources receive the pinned image tag securely.
## 2026-05-04 - [Hardened dd-sync CronJob with strict NetworkPolicy]
**Cluster Quirk:** The `dd-sync` CronJob was missing a NetworkPolicy. Without one, pods default to allowing all ingress and egress traffic. In this cluster environment, allowing all egress for a sync job is dangerous if compromised.
**Learning:** CronJobs require targeted NetworkPolicies just like Deployments. A default 'deny-all' ingress policy paired with an explicit allow-list for egress (HTTPS on 443, DNS on 53) ensures least privilege for background tasks connecting to external resources (Databricks, Entra ID).
**Resilience:** Created `networkpolicy-sync.yaml` to specifically target `app: dd-sync` enforcing these strict ingress/egress controls, validated via `kube-score`.
## 2026-05-07 - [Fixed HPA Replica Conflict and Added PodDisruptionBudget]
**Cluster Quirk:** The `dd-app` deployment had a hardcoded `replicas: 2` set in its spec while concurrently being targeted by a HorizontalPodAutoscaler (`dd-hpa`). In addition, the deployment was missing a PodDisruptionBudget (PDB) to ensure high availability during node drains or maintenance.
**Learning:** Statically setting a `replicas` count in a Deployment managed by an HPA causes conflicts, where scaling events during rollouts or apply commands forcefully reset the pod count, ignoring HPA's intended state. PodDisruptionBudgets are essential to pair with HPAs to guarantee that scaling down or evicting pods doesn't lead to total service disruption.
**Resilience:** Removed the `replicas` field from `deployment.yaml` to allow the HPA to natively manage pod counts. Added `pdb.yaml` with `minAvailable: 1` to ensure at least one instance remains available during cluster disruptions.
## 2026-05-08 - [Hardened NetworkPolicy for Background Workers]
**Cluster Quirk:** The `dd-sync-worker` background process (Deployment) shared the same restrictive egress requirements (HTTPS on 443, DNS on 53) and deny-all ingress posture as the `dd-sync` CronJob, but was missing a NetworkPolicy entirely. Without explicit NetworkPolicy coverage, pods default to allowing all ingress and egress traffic, exposing a potentially powerful background process to unnecessary lateral movement risks.
**Learning:** NetworkPolicies are tied strictly to label selectors (`podSelector`). When introducing a new workload architecture (like splitting a CronJob into a background daemon deployment `dd-sync-worker` and a nightly resync `dd-sync`), `matchLabels` might only cover one resource. `matchExpressions` allows a single, strict NetworkPolicy to comprehensively cover multiple related background components that share the same security posture.
**Resilience:** Upgraded the `dd-sync-network-policy` to use a `matchExpressions` selector targeting both `dd-sync` and `dd-sync-worker`, ensuring that any new replica or run of these processes is automatically isolated from unexpected ingress while explicitly allowing essential external egress.
## 2024-05-15 - Streamlit with readOnlyRootFilesystem

**Cluster Quirk:** Streamlit workloads crash at startup when the container is run with a read-only root filesystem, because the app attempts to write temporary files (like cache files) dynamically at runtime.

**Learning:** This is a common quirk with applications that aren't natively designed to run immutably, requiring write access to temporary directories. The K8s API will enforce the read-only restriction rigidly, preventing the container from starting.

**Resilience:** To run Streamlit securely with `readOnlyRootFilesystem: true`, an `emptyDir` volume must be mounted to `/tmp` in the deployment manifest. This allows the root filesystem to remain immutable while providing the necessary write-access for temporary runtime files.
