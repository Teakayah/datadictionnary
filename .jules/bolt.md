## 2024-05-17 - Pandas Iteration Performance
**Learning:** Found widespread use of `iterrows()` in this app, which caused bottlenecks when repeatedly rendering Streamlit components or performing database inserts. Using `iterrows()` forces pandas to box every row into a Series, introducing significant overhead.
**Action:** Always replace `iterrows()` with `itertuples(index=False)` for loop iteration (using `getattr` instead of `dict.get` for safe access), and use `df.to_dict('records')` when directly mapping DataFrames for database batch executions like `cursor.execute_write`. This pattern significantly increases loop speeds and reduces memory overhead.## 2024-05-08 - Bulk Insert Pandas Dataframes to DuckDB via Registration
**Learning:** Iterating over Pandas Dataframes to insert row-by-row (`df.to_dict('records')` + `execute_write`) triggers an N+1 query problem, severely throttling performance in DuckDB inserts (especially during data sync/loading tasks). DuckDB natively supports registering Pandas DataFrames as virtual tables via the connection object.
**Action:** Always use DuckDB's `.register()` feature to bind the DataFrame to a temporary name (using a unique ID like `uuid.uuid4().hex` to prevent multi-thread collisions), and then perform a single `INSERT INTO table ({cols}) SELECT * FROM tmp_view`. Always specify target column names explicitly to prevent schema alignment crashes. Also gracefully fallback to `df.to_dict` if the connection mock doesn't support `.register`.
## 2024-05-18 - N+1 database queries when querying multiple tables
**Learning:** Found an N+1 query problem in `dr_resync.py` when attempting to fetch maximum timestamps for multiple tables individually. Making separate database calls in a loop severely throttles performance.
**Action:** Always group queries into a single batched query using `UNION ALL` when fetching aggregate data (like maximum timestamps) across multiple tables, reducing the overhead of database connections and network latency.
## 2024-05-10 - DuckDB N+1 Query Overhead
**Learning:** Executing multiple separate DuckDB queries via `run_query` incurs noticeable overhead due to connection locking and repeated pandas DataFrame instantiations. In UI components like the admin dashboard that fetch multiple independent counts, this N+1 pattern was causing ~50% slower execution times.
**Action:** When fetching multiple scalar values or independent counts from DuckDB, consolidate them into a single query using subqueries in the `SELECT` clause (e.g. `SELECT (SELECT COUNT(*) FROM t1) AS c1, ...`) to eliminate connection and dataframe conversion overhead.
