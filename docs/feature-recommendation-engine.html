Activity-Based Recommendation Engine

Table of contents

  1. Description
  2. How it works
  3. Implementation logic
  4. Security and personalization

Description

The Recommendation Engine surfaces popular and active data assets to users, encouraging the discovery of high-value tables within their authorized scope. It powers the Recommended sub-tab in the Discovery interface.

How it works

The engine uses a popularity-based heuristic derived from organization-wide activity, rather than complex collaborative filtering. This ensures relevance even with smaller user bases. For technical details on the activity store, see the Architecture Overview.

Self-starting. Because it relies on the audit log rather than training data, the engine starts producing recommendations as soon as users begin interacting with the catalog.

1. Activity aggregation

The engine queries the user_data.audit_log to identify tables with the highest recent engagement. It specifically tracks:

  • Metadata Edits — Changes to table descriptions or column business names.
  • Social Signals — New comments or threaded replies added to a table.

Implementation logic

The recommendation is performed via a single SQL query against the local DuckDB cache. The query aggregates events and ranks objects by their total engagement count.

SELECT object_name, COUNT(*) AS engagement_score
FROM user_data.audit_log
WHERE event_type IN (
  'table_description_change', 
  'business_name_change', 
  'comment_added'
)
GROUP BY object_name 
ORDER BY engagement_score DESC 
LIMIT 30;

Security and personalization

To ensure recommendations are both safe and helpful, the engine applies two layers of filtering in the application layer before rendering. See the User Guide for the end-user experience.

1. Authorization filter

Results are cross-referenced with the permissions_cache. A user only ever sees recommendations for tables they are authorized to access. This follows our push-down authorization principle.

2. Novelty filter (Novelty)

Tables that appear in the user's "Recently Viewed" list (the last 5 interactions) are excluded. This prevents the engine from recommending assets the user is already actively using, prioritizing the discovery of new high-value data.
