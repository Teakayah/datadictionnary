§ 1 — Overview

What is the Data Dictionary?

The Data Dictionary is an internal web application that gives everyone in the organisation a searchable, plain-English view of the data assets held in Databricks Unity Catalog. It shows you which tables exist, what they contain, who owns them, and who is allowed to access them — without requiring any technical knowledge of Databricks or SQL. For a high-level summary of the product goals, see the Product Overview.

All results are automatically filtered to the tables you have permission to see. You will never encounter a table you cannot access, and you will never be asked to request access to something you already have. This "push-down" security model is detailed in ADR 002.

Synced nightly. Catalog metadata (table names, descriptions, column types, grants) is refreshed every night from Unity Catalog. Changes you make via inline editing are applied immediately in the app and pushed to Databricks in the background by the Sync Worker.

§ 3 — Getting started

Getting started

The Data Dictionary uses your organisation's Entra ID (Microsoft Azure AD) account. No separate username or password is required.

Sign in

  1. Open the Data Dictionary URL in your browser.
  2. Click Sign in with Entra ID.
  3. Complete the Microsoft authentication flow (your browser may already have a session and skip this step).
  4. You are redirected to the search page. The catalog is ready to use.
No tables visible? If you see "You don't have access to any tables yet", your account has not been added to a data-access group. Contact your data platform administrator and ask them to add you to the appropriate group in Entra ID.

§ 4 — How to

Search the catalog

  1. Click the Search tab in the navigation bar.
  2. Type a table name, column name, or business term in the search box. Results appear as you type.
  3. Results are sorted by relevance: exact name matches rank first, then prefix matches, then partial matches. Glossary terms appear below table results.
  4. Click View details → on any result to open the full table detail page.
Tip. Use the Catalog browser for browsing by schema, or Discovery for exploring tables your colleagues are actively working with.

Read a table detail page

The detail panel opens on the right side of the Search page when you select a result. It contains:

  1. Header: full Unity Catalog identifier (catalog.schema.table), table type (TABLE / VIEW), and freshness timestamp.
  2. Description & steward: the table description and the email address of the person responsible for this table.
  3. Columns: every column with its data type, Unity Catalog comment, business name override, and definition. Power users see an edit icon next to each field.
  4. Grants: the list of Entra principals (users and groups) with access to this table and their privilege level.
  5. Lineage: upstream tables that feed this table and downstream tables that consume it, up to two hops in each direction.
  6. Downstream impact: a count of dependent assets in the blast radius. A warning appears if any certified or production table is downstream.
  7. Data quality: the latest DQ grade (A–F) when Lakehouse Monitoring data is available.
  8. Data sample: top 100 rows from the table, visible only if you have SELECT on it.
  9. Export: the Export schema button downloads a CSV with column names, types, comments, and business names.

Bookmark and track tables

  1. Open the table detail page for any table.
  2. Click the Bookmark button (star icon) near the table header.
  3. The table is saved to your personal bookmarks list, accessible from Discovery → My Bookmarks.
  4. To remove a bookmark, click the Bookmarked button on the same table — it toggles off.
Recently Viewed is updated automatically every time you open a detail page. No action required — just browse and your history builds itself.

Leave a comment or question

  1. Open the table detail page for the table you want to comment on.
  2. Scroll to the Comments section at the bottom of the detail panel.
  3. Type your comment in the text area (max 1,000 characters) and click Send.
  4. To reply to an existing comment, click Reply beneath it.
Notification. The table steward receives an email notification for new comments when SMTP is configured by your platform team. Email failures do not block the comment from being saved.

§ 5 — FAQ

Frequently asked questions

Why can I not see any tables?

Your Entra ID account is not assigned to any data-access group. Contact your data platform administrator and ask to be added to the appropriate group. If you were just added, sign out and sign back in — the app refreshes your group memberships on each new sign-in.

I was recently added to a group but still see no change.

Sign out using the Sign out link in the navigation bar, then sign back in. The app caches your group memberships for up to one hour; signing out clears your personal cache immediately. If the problem persists after re-signing in, ask an admin to flush the group-permissions cache from the Admin dashboard.

A table I know I can access in Databricks does not appear in the search results.

The Data Dictionary only shows tables with an explicit SELECT or MODIFY grant for your group in Unity Catalog, or tables marked SELECT_ALL_USERS. Databricks-level access via workspace roles is not reflected here. Ask your data engineer to grant the appropriate Unity Catalog privilege to your group.

The table description I see seems outdated.

Catalog metadata syncs nightly from Unity Catalog. If you made a change in Databricks directly (outside the Data Dictionary), it will appear at the next sync. If you updated it via the Data Dictionary's inline editor, it should be visible immediately and pushed to Databricks within minutes.

I submitted a metadata change but it is not visible to others.

Column business name and definition changes submitted by non-admin editors require admin approval before they are published. Check with your admin — the proposal is waiting in the pending-reviews queue in the Admin dashboard.

What does the data quality grade mean?

Grades A–F are derived from Lakehouse Monitoring checks run against the table. A = 90–100 % pass rate, B = 75–89 %, C = 60–74 %, D = 45–59 %, F = below 45 %. If no monitoring data is available, no badge is shown. Contact your data quality team for details on specific checks.

I cannot see the Admin tab.

The Admin tab is only visible to members of the ADMIN_GROUPS environment variable. Ask your platform administrator if you need admin access.

I cannot edit table or column metadata.

Inline editing is available to members of EDITOR_GROUPS. It may also be temporarily disabled globally by an admin (e.g., during a catalog migration). Check with your admin if the edit icon is missing from fields you expect to be able to edit.

§ 1 — Role

What is a data steward?

A data steward is the person responsible for the accuracy, completeness, and trustworthiness of a set of data assets. In the Data Dictionary, stewardship is expressed through two things: your email address appears in the Steward field on each table you own, and you are notified whenever a user leaves a comment or question on those tables. For a high-level summary of the product goals, see the Product Overview.

You do not need to be a data engineer to be a steward. Your job is to describe what the data means in business terms — what a table is for, what each column represents, what caveats or limitations apply. The engineering team handles the technical structure. See the User Guide for more on user-facing features.

Your stewardship shows up everywhere. The description and steward email you write appear in search results, the discovery feed, the health dashboard, and the glossary. Good stewardship directly improves findability for every user in the organisation.
§ 2 — Getting oriented

Finding your tables

There are two ways to find the tables assigned to you. If you are an administrator, see the Admin Runbook for higher-level management tasks.

Via Search

  1. Open the Search tab and type the table name or schema.
  2. Click View details → to open the detail panel.
  3. Confirm your email appears in the Steward field. If it is blank or incorrect, update it (see § 4).

Via the Health dashboard

  1. Open the Health tab.
  2. The Priority actions panel lists tables in your accessible groups that are missing descriptions — these are likely your most urgent stewardship tasks.
  3. Click any table name in the priority list to jump directly to its detail page.
Not seeing your tables? Your view is filtered to the groups your Entra ID account belongs to. If a table you own is not visible, contact your platform administrator to verify the Unity Catalog grants for your group. See ADR 002 for details on the security model.
§ 3 — Writing

Writing good table descriptions

A table description answers three questions: what is in this table, where does it come from, and when is it updated. Business users should be able to decide whether to use the table from the description alone, without opening it.

How to update a description

  1. Open the table detail page.
  2. Click the pencil icon next to the Description field.
  3. Type or paste your description (no hard limit, but 1–3 sentences is ideal).
  4. Click Save. The change is visible immediately and pushed to Unity Catalog within minutes.

Do and do not

Do
  • State what the table contains in the first sentence
  • Mention the source system or feed
  • Note update frequency (nightly, real-time, on-demand)
  • Flag known caveats or exclusions
  • Use sentence case and plain language
Do not
  • Repeat the table name as the entire description
  • Use acronyms without defining them
  • Reference internal ticket numbers or sprint names
  • Write in first person ("I created this table…")
  • Leave the description as the auto-generated placeholder

Examples

Good: One row per confirmed customer order placed via the web or mobile channels since 2021. Excludes internal test orders. Updated nightly from the transactional database via the orders ETL pipeline.
Needs work: Orders table. Contains order data. Created by the data team.

Updating the steward field

  1. Open the table detail page and click the pencil icon next to Steward.
  2. Enter the email address of the person responsible for this table (you, or a colleague).
  3. Click Save.
Use a shared mailbox or team address if available. If you set your personal email and then leave the team, comments will stop reaching anyone. A team distribution list ensures continuity.
§ 4 — Columns

Column business names and definitions

Column names in Unity Catalog are often technical identifiers (cust_ltv_90d, acq_src_cd). Business names and definitions translate these into language that business users can understand and trust.

Business name vs. definition

Business name

A short, human-readable label. Replaces the technical column name in the UI. Max 255 characters. Example: 90-day customer lifetime value

Definition

A full explanation of what the column contains, how it is calculated, and any caveats. Max 2,000 characters. Example: Sum of all revenue attributed to the customer in the 90 days prior to the reference date, net of refunds. Null if the customer has fewer than 3 orders.

How to add or update a column override

  1. Open the table detail page and scroll to the Columns section.
  2. Click the pencil icon next to the column's business name or definition field.
  3. Enter your text and click Save.
  4. If you are an admin: the change publishes immediately and syncs to Databricks. If you are a power user: the change is submitted as a proposal and appears in the admin approval queue.
Proposals are not visible to other users until approved. You will see your proposed value immediately in your own session (marked as pending), but other users continue to see the previous value until an admin approves it.
§ 5 — Workflow

The metadata approval workflow

Column business name and definition changes from non-admin editors go through a lightweight review before publication. Table-level changes (description, steward) publish immediately.

What happens at each stage

  • Pending approval: The proposed value is stored in user_data.business_name_overrides with status='pending_approval'. It is visible only to the submitting editor (in their session) and to admins in the review queue.
  • Approved: An admin clicks Approve. The status changes to 'published', an audit event is logged, and the change is added to the sync queue. See the Admin Runbook for the approval interface.
  • Synced: The Sidecar sync worker pushes the change to Unity Catalog as a column comment within minutes.
  • Rejected: The admin clicks Reject. The proposed value is deleted. An audit event records the rejection. The column retains its previous value.

Checking the status of your proposal

Open the table detail page and find the column you edited. If your proposal is pending, the field shows your proposed value with a subtle pending indicator. Once approved, the value is published and shows normally. If rejected, the field reverts to the previous value — you will need to resubmit with a revised value. For more on the background synchronization process, see the Architecture Overview.

Table descriptions and steward updates bypass approval. These changes go live instantly and sync to Databricks in the background, without requiring admin review.
§ 6 — Communication

Handling comments and questions

Users can leave questions, flags, or notes on any table or column you steward. When SMTP is configured, you receive an email notification for each new comment. Replies also trigger notifications.

Finding comments on your tables

  1. Open the table detail page for any table you steward.
  2. Scroll to the Comments section at the bottom of the detail panel.
  3. All comments and replies are shown in chronological order.

Responding to a comment

  1. Click Reply beneath the comment you want to respond to.
  2. Type your reply (max 1,000 characters) and click Send.
  3. The person who left the original comment is notified by email.

Comment triage guide

  • "What does this column mean?" → Add or improve the column definition (see § 4). Reply with a brief answer and note that you've updated the definition.
  • "This table seems outdated." → Check the freshness field on the table detail page. If the nightly sync is working correctly, the data is as fresh as Unity Catalog. Reply with the update cadence from the table description.
  • "I see unexpected nulls in column X." → Flag this to your data engineering contact. Update the column definition with a caveat note once you have an answer.
  • "Can I get access to this table?" → Access is managed in Entra ID, not in the Data Dictionary. Direct the user to their manager or the data platform team.
§ 7 — Audit trail

Tracking changes via audit log

Every metadata change — description updates, column override proposals, approvals, rejections — is recorded in the audit log with the actor's email, timestamp, and before/after values. Admins can view the full log in the Admin panel.

What is logged

  • Table description change — actor email, old description, new description, timestamp
  • Table steward change — actor email, old steward, new steward, timestamp
  • Business name change — actor email, column identifier, old value, new value, timestamp (also records approvals and rejections)
  • Comment added / reply added — actor email, table identifier, timestamp

Requesting an audit extract (admins only)

The full audit log is accessible in the Admin dashboard → Audit Logs tab. If you need a CSV extract or a historical view beyond what the UI shows, ask your platform administrator to query user_data.audit_log or the Databricks mirror at data_governance.dictionary_cache.audit_log directly. See the Admin Runbook for more on audit management.

§ 8 — Coverage monitoring

Using the Health dashboard

The Health tab shows documentation coverage across the entire catalog — broken down by schema. It is the fastest way to find your gaps and prioritise your stewardship effort. Technical details on the coverage calculation can be found in the Architecture Overview.

Reading the metrics

  • Table coverage % — percentage of tables in your accessible schemas that have a non-empty description.
  • Column coverage % — percentage of columns across those tables that have a business name or definition override.
  • Schema breakdown — a table showing total / described counts per schema. Sort by the coverage column to find the most under-documented schemas.

Using the Priority actions panel

  1. The panel lists up to 5 undocumented tables — these are the tables with the highest interaction activity (views, comments, edits) that still lack a description.
  2. Click any table name to open its detail page directly.
  3. Add a description and save. The table disappears from the priority list on the next page load.
Tip. High-interaction undocumented tables cause the most user confusion. Addressing the Priority actions list first has the highest return on your stewardship time.
§ 9 — Style guide

Best practices and style guide

Voice and tone

Write as if you are explaining the data to an intelligent colleague who is not a data engineer. Factual, specific, and brief. No jargon without definition. No internal project names that will lose meaning in 6 months.

Naming conventions

  • Business names: title-style capitalisation for proper nouns, otherwise sentence case. Customer lifetime value, not Customer Lifetime Value and not CLV.
  • Definitions: full sentences. End with a period. State the unit of measure where relevant (in USD, in days, as a percentage).
  • When an acronym is widely understood in your organisation (e.g., SKU, CRM), you can use it — but define it on first use in the table description.

What belongs in a description vs. a comment

  • Description: stable facts about the data — what it is, where it comes from, how often it updates, known caveats.
  • Comment: time-sensitive notes, open questions, or flags that may be resolved — not permanent documentation.

Keeping descriptions current

Descriptions drift as data structures change. A practical habit: whenever you modify a table's schema in Unity Catalog, update the table description in the Data Dictionary in the same session. If a column is deprecated or renamed, update its business name and add a deprecation note to the definition.

Review cadence

A quarterly sweep of your tables is enough for most stewards: check that descriptions are still accurate, that the steward email is current, and that any columns added since the last review have business names and definitions. The Health dashboard makes this quick — a schema with 100 % coverage takes minutes to verify, not hours.

§ 1 — Sync

Sync queue monitoring

The Sidecar sync worker drains user_data.pending_sync and pushes changes to Databricks. The Admin dashboard → Operations tab shows live queue stats. For a high-level summary of the product goals, see the Product Overview.

Reading the sync panel

MetricMeaningNormal range
PendingRows waiting to be processed0–10 under normal load
ProcessingRows currently in flight (status = 'syncing')0–5
DoneSuccessfully pushed to Databricks in this sessionAny
FailedRows that exhausted 3 retry attempts0 — investigate immediately
HeartbeatLast time the sidecar wrote to worker_heartbeat< 60 s ago

Heartbeat stale — worker is down

Symptom: Heartbeat shows > 60 s ago or "Daemon offline". The k8s liveness probe will restart the pod automatically. If it stays offline, check the pod logs. See ADR 004 for architecture details.
  1. Check the sidecar pod status: kubectl get pods -l app=dd-sync-worker
  2. Read logs: kubectl logs deploy/dd-sync-worker --tail=100
  3. Common causes: DuckDB file lock contention, Databricks credential expiry, OOM. Address the root cause. See the Sync Worker Runbook for detailed troubleshooting.
  4. If the pod is in CrashLoopBackOff, check USER_DATA_PATH is correctly mounted and the PVC is healthy.
  5. The worker restores itself on restart — no manual queue intervention needed unless rows are stuck in 'syncing' state.

Failed rows

  1. Failed rows are visible in the sync panel table. Note the object_type and object_name.
  2. Query directly: 
    SELECT * FROM user_data.pending_sync WHERE status = 'failed';
  3. Check the last_error column for the rejection reason from Databricks (most common: invalid identifier, privilege error, or token expiry).
  4. Fix the underlying cause (e.g., re-grant MODIFY on the target table), then reset the row: 
    UPDATE user_data.pending_sync SET status = 'pending', attempt_count = 0 WHERE status = 'failed';
  5. The worker will pick it up on the next poll cycle (default 5 s active, 30 s idle).
§ 2 — Recovery

Stale-row recovery

A row stuck in 'syncing' for more than 5 minutes (configurable via SYNC_STALE_ROW_S) is automatically flipped back to 'pending' at the top of each worker cycle. This handles crashes mid-flight without manual intervention.

Manual recovery (if auto-recovery fails)

  1. Identify stuck rows: 
    SELECT * FROM user_data.pending_sync
WHERE status = 'syncing'
  AND updated_at < NOW() - INTERVAL 10 MINUTES;
  2. Reset them manually: 
    UPDATE user_data.pending_sync
SET status = 'pending'
WHERE status = 'syncing'
  AND updated_at < NOW() - INTERVAL 10 MINUTES;
  3. Confirm the worker picks them up within one poll cycle. Watch the heartbeat timestamp in the Admin panel.
Do not delete rows from pending_sync unless you intentionally want to abandon a change. Deletion bypasses the audit trail.
§ 3 — DR resync

DR resync management

Every 20 worker cycles the sidecar runs a DR resync: it pulls the current audit log, business-name overrides, and table-metadata overrides back from Databricks into the local DuckDB file. This keeps the local cache consistent with the source of truth after a pod restart or PVC swap.

Reading resync status

StatusMeaning
okLast resync completed without errors.
runningResync in progress (completes in seconds under normal load).
errorLast resync failed. Check worker logs for the specific SQL error.
neverWorker has not yet run a resync cycle (normal on first boot).

Force a resync immediately

  1. Run the worker in single-cycle mode: python -m src.sync.daemon --once
  2. Or restart the sidecar pod — it runs a full cycle on startup.
  3. Confirm status changes to ok in the Admin panel within 30 s.

Resync fails repeatedly

  1. Check worker logs for the SQL error. Common causes: Databricks SQL Warehouse offline, token expired, schema version mismatch.
  2. Verify the warehouse is running: open Databricks UI → SQL Warehouses → confirm state is Running.
  3. Check token expiry: kubectl get secret dd-databricks-secret -o yaml and verify DATABRICKS_TOKEN is not expired.
  4. If schema has drifted, run python scripts/nightly_sync.py manually to recreate dictionary_cache tables with the correct schema.
§ 4 — Access control

Group-cache operations

The application caches each user's Entra ID group memberships in process memory for 1 hour (keyed by user OID). This prevents repeated Graph API calls for every page load. The cache is cleared per-user on sign-out. See ADR 006 for detailed identity architecture.

When to flush the cache

  • A user was added to or removed from an Entra group and needs immediate access change (without waiting up to 1 hour).
  • You performed bulk group changes (e.g., during an org restructure) and want all users to see the new state.
  • A user reports seeing tables they should no longer have access to.

Flush via Admin dashboard

  1. Open the Admin tab → Operations → Group cache section.
  2. Click Flush group cache. This clears all cached group memberships for all active users.

Troubleshooting reference

User sees tables they should not have access to

Likely cause: stale group cache. Flush via Admin → Operations → Group cache → Flush group cache. If the problem persists after the user signs out and back in, verify the Unity Catalog grant has actually been revoked for their group.

1. What it is

Data Dictionary is an internal web application that gives non-technical business users a searchable, business-language view of the data assets available to them in Databricks Unity Catalog.

Users sign in with their Microsoft Entra ID account and immediately see only the tables and columns they are already authorized to access — no new permission model, no IT tickets. They can search across thousands of tables in milliseconds, read and write business definitions, preview data samples, monitor pipeline runs, and receive curated announcements from data stewards, all from a single browser tab.

Core proposition in one sentence: replace a daily tax of Slack threads and shadow spreadsheets with a 2-minute self-service lookup.

2. Why it exists

The problem

Non-technical staff at the organisation cannot reliably find or understand the data assets they have access to in Databricks Unity Catalog. The native Unity Catalog UI is engineering-oriented: it exposes physical schema, internal IDs, and admin-flavored surfaces that make routine business questions ("which table holds approved invoices?", "who is the steward of this column?") expensive to answer.

The result is a measurable daily cost:

  • Repeated #ask-data Slack threads directed at data engineers
  • Duplicated reports built from different, incompatible source tables
  • Shadow data dictionaries maintained in spreadsheets that drift from reality

    The goal

    A single, search-first, business-language view of the catalog that:
    1. Exposes only the data the user is already entitled to see (Entra ID groups + Unity Catalog grants) — no new permission model.
    2. Lets non-technical users discover, understand, and reference tables and columns without writing SQL or talking to data engineering.
    3. Lets data stewards keep business definitions current without raising a ticket against the data platform team.

4. Feature map

F1 — Search and discovery

Full-text search across catalogs, schemas, table names, column names, descriptions, and business-glossary terms. Results are returned in under 500 ms (p95) and are permission-filtered — the user only sees what they are authorized to access.

The Discovery tab has four sub-tabs:

  • Recommended — tables ranked by recent edit and comment activity across the organisation, excluding tables the user has already viewed (surfaces genuinely new assets)
  • Notable — recently updated tables scoped to the user's primary group
  • My bookmarks — tables and columns the user has starred
  • Recently viewed — chronological navigation history A CMS banner above the sub-tabs allows admins to publish pinned announcements, featured tables, and guides with configurable expiry (2 / 7 / 30 days or never).

    F2 — Permission-trimmed visibility

Every result-returning SQL query JOINs the permissions cache, so unauthorized rows are excluded inside the database engine before any data leaves the SQL layer. Users with more than 150 Entra group memberships (the "overage" case) are handled transparently via a Microsoft Graph API fallback — they see the same results as any other user, with no manual intervention required.

The sentinel principal SELECT_ALL_USERS marks tables that are publicly accessible to all authenticated users.

F3 — Table detail view

Per-table page showing:
  • Catalog / schema / table identifier (monospace)
  • Description, steward, table type, freshness
  • Full column list with data type, Unity Catalog comment, business name override, and definition override
  • Grant list (who can access the table and with what privilege)
  • Multi-hop lineage (upstream / downstream tables) — powered by a single recursive SQL CTE, replacing a previous N+1 hop-by-hop query pattern
  • Downstream impact summary — count of downstream assets in the blast radius, with a warning when certified or production tables are affected
  • Data quality grade badge (A–F) when DQ data is available (sourced from Lakehouse Monitoring or Unity Catalog tags)
  • Data sample — top 100 rows, shown only if the user has SELECT on the table
  • CSV export of the schema including business names and definitions

    F4 — Inline metadata editing with approval workflow

Power users (members of EDITOR_GROUPS) can edit:
  • Table description and steward — written immediately to a local overrides table (user_data.table_metadata_overrides) and pushed to Unity Catalog by the sidecar
  • Column business name (max 255 chars) and definition (max 2000 chars) Approval workflow for column overrides: admins publish directly and changes sync to Databricks immediately. Non-admin power users create a pending_approval proposal that appears in the admin review queue. Admins approve or reject from the Admin dashboard; only approved changes are pushed to Unity Catalog. Every edit (and every approval / rejection) produces an audit-log entry with actor email, timestamp, and before/after values. Admins can globally disable editing (e.g., during a data migration) without redeploying.

    F5 — Comments

Any authenticated user can leave a question or flag on any table or column (max 1000 chars), with one level of threaded replies. New comments trigger an email notification to the table steward when SMTP is configured; email failures do not block the comment from being saved.

6. Security model

Push-down SQL authorization

No Python-side filtering. Every query that returns table-level results uses this pattern:

SELECT t.full_name, t.description, t.table_type
FROM tables_metadata t
JOIN permissions_cache p ON p.full_name = t.full_name
WHERE p.principal IN (%(group_1)s, %(group_2)s, 'SELECT_ALL_USERS')
  AND t.full_name ILIKE %(query)s
GROUP BY t.full_name, t.description, t.table_type

Unauthorized rows are discarded by the database engine before any data reaches the application. A bug in Python cannot accidentally expose unauthorized rows. Pagination and row counts are correct from the first query. Every logged SQL statement is self-contained and shows exactly which groups were evaluated — fully auditable. (ADR 002)

Feature-level access control (three tiers)

Every write function raises PermissionError at the function boundary — independent of the UI gate.

Entra ID groups overage

Microsoft Entra omits the groups claim in the ID token when a user belongs to more than ~150 security groups. Without handling, those users see zero tables and receive no error message — a silent production failure.

The app detects this shape (_claim_names.groups present, groups absent) and calls POST /v1.0/me/getMemberObjects {"securityEnabledOnly": true} to retrieve the full transitive list via Microsoft Graph. Results are cached per user OID for 1 hour in a process-level lock-protected dict (not @st.cache_data, which is session-scoped and would defeat the purpose). On any Graph failure — network, 4xx, 5xx — the app returns an empty group list and the user sees no tables. We never silently grant access on failure. (ADR 006)

Admins can flush the entire group cache from the admin page. Sign-out clears the individual user's entry so "sign out and sign back in" always reflects current Entra state.

Additional hardening

  • User-supplied display values are HTML-escaped before rendering
  • SMTP headers are sanitized to prevent header injection in comment notification emails
  • Parameterized queries throughout; _to_duckdb_sql() preserves the parameterized pattern across both backends (no string concatenation)
  • Kubernetes NetworkPolicy restricts egress to HTTPS only and ingress to the ingress controller namespace

9. Key architectural decisions

The full rationale for each is in docs/adr/.

ADR 001 — DuckDB as the local metadata cache

Decision: Serve all read queries from an embedded DuckDB file rather than routing every request to the Databricks SQL Warehouse over the network.

Why: The catalog (~800 tables, ~15 columns each, ~3 000 permission rows) fits comfortably on local disk. DuckDB runs in-process with no server, speaks SQL, and handles the analytical join patterns (GROUP BY, multi-table JOIN, UNION) the app needs. Search queries hit p95 < 8 ms locally versus ~300 ms over the network.

Trade-off: Requires a shared ReadWriteMany PVC when running multiple Streamlit replicas. The catalog file is replaced atomically by the sync job, so readers always see a consistent snapshot; during the swap window (30–90 s) they continue reading the previous file.

ADR 002 — Push-down SQL authorization

Decision: Enforce permissions via a JOIN inside the SQL engine, not by fetching all results and filtering in Python.

Why: A Python filter is a single point of failure — one bug exposes unauthorized rows. Push-down SQL means unauthorized rows are mathematically impossible to return. Row counts and pagination are correct from the first query without reading all results first.

ADR 003 — Streamlit, not FastAPI

Decision: Build the UI with Streamlit rather than a separate React/FastAPI stack.

Why: The target user base needs a read-mostly, form-driven catalog browser — not a real-time collaborative editor. Streamlit delivers that in one Python process with no client–server API boundary. The trade-off (limited UI flexibility, no server-sent events) is acceptable given the use case. Engineers familiar with Python can maintain the UI without learning a JavaScript framework.

ADR 004 — Sidecar sync worker

Decision: Move the write-back loop out of the Streamlit process into a separate sidecar process.

Why: The previous in-process daemon thread shared a Streamlit-cached DuckDB connection with the UI (corrupting concurrent reads), ran without a Streamlit ScriptRunContext (undefined behaviour), and tracked UI activity in two diverging state objects. A separate process with its own DuckDB connection and a clear queue-based interface eliminates all three problems. The Streamlit pods are now read-only from Databricks' perspective; the sidecar is the sole intentional writer.

ADR 005 — Per-entity storage abstraction

Decision: Replace ~13 duplicated three-way switches (demo / DuckDB / Databricks) across four modules with per-entity Protocol-based backends and factory functions.

Why: Each entity had a slightly different exception-handling shape, so a fix to one didn't reach the others. Tests were brittle because they mocked _duckdb_available directly. The Protocol pattern makes adding a new entity mechanical (define → implement Demo/DuckDB/Fake → add factory), and tests now inject Fake*Storage directly without touching routing internals.

ADR 006 — Entra ID groups overage handling

Decision: Detect the _claim_names.groups pointer in the ID token and call Microsoft Graph getMemberObjects when the inline groups claim is absent.

Why: Entra omits the inline groups claim for users with >150 group memberships. Without this handling, those users see zero tables with no error — a silent, invisible production failure that only affects enterprise users (IT admins, partner teams). The Graph fallback is cached per-user for 1 hour, fail-closed on any error, and clears on sign-out.

Problem statement

Non-technical staff at the organisation cannot reliably find or understand the data assets they have access to in Databricks Unity Catalog. The native Unity Catalog UI is engineering-oriented: it exposes physical schema, internal IDs, and admin-flavoured surfaces that make routine business questions ("which table holds approved invoices?", "who is the steward of this column?") expensive to answer. The result today is a tax of repeated #ask-data Slack threads, duplicated reports, and shadow data dictionaries maintained in spreadsheets.

We need a single, search-first, business-language view of the catalog that:

  1. Exposes only the data the user is already entitled to see (Entra ID + Unity Catalog grants). No new permission model.
  2. Lets non-technical users discover, understand, and reference tables and columns without writing SQL or talking to data engineering.
  3. Lets data stewards keep business definitions current without raising a ticket against the data platform team.

Feature: Activity-Based Recommendation Engine

Description

The Recommendation Engine surface's popular and active data assets to users, encouraging the discovery of high-value tables within their authorized scope. It powers the "Recommended" sub-tab in the Discovery interface.

How it Works

The engine uses a popularity-based heuristic derived from organization-wide activity, rather than complex collaborative filtering. This ensures relevance even with smaller user bases.

1. Activity Aggregation

The engine queries the user_data.audit_log to identify tables with the highest recent engagement. It specifically tracks:
  • Metadata Edits: Changes to table descriptions or column business names.
  • Social Signals: New comments or threaded replies added to a table.

    2. Personalization & Security

To ensure the recommendations are safe and helpful, the engine applies two layers of filtering:
  • Authorization Filter: Results are cross-referenced with the permissions_cache. A user only ever sees recommendations for tables they are authorized to access.
  • Novelty Filter: Tables that appear in the user's "Recently Viewed" list (last 5 interactions) are excluded. This prevents the engine from recommending assets the user is already actively using.

    3. Implementation Logic

The recommendation is performed via a single SQL query against the local DuckDB cache: 
SELECT object_name, COUNT(*) AS engagement_score
FROM user_data.audit_log
WHERE event_type IN ('table_description_change', 'business_name_change', 'comment_added')
GROUP BY object_name 
ORDER BY engagement_score DESC 
LIMIT 30;

Core components

Identity and security layer

Authentication uses the OAuth 2.0 / OpenID Connect flow against Microsoft Entra ID. The app extracts Security Group Object IDs from the groups claim in the ID token. No additional database lookup is needed to resolve group membership — the signed token is the proof. Comma-separated group env vars (ADMIN_GROUPS, PIPELINE_GROUPS, EDITOR_GROUPS) are parsed by _parse_groups(), an LRU-cached helper in src/auth.py, so the string splitting cost is paid once per unique env value rather than on every RBAC check.

In local development, setting ENABLE_MOCK_AUTH=true and ENVIRONMENT=development replaces the Entra ID redirect with department-specific mock login buttons (finance, research, hr, it).

Metadata sync job

scripts/sync_metadata.py uses the databricks-sdk (WorkspaceClient) to crawl the Unity Catalog hierarchy: catalogs → schemas → tables → columns → grants → lineage edges. Output is written to:

  • The Databricks data_governance.dictionary_cache schema (truncate-and-reload via SQL Warehouse)
  • A local DuckDB file at DUCKDB_PATH (atomic swap via os.replace so in-flight reads are never interrupted)

A separate script, scripts/nightly_sync.py, is the entry point for the CronJob container. The in-app DR resync worker is a different, lighter process (see sidecar below).

DuckDB local cache layer

When DUCKDB_PATH is set, the app serves all read queries from a local DuckDB file instead of routing them across the network to the SQL Warehouse. This reduces median query latency from ~300 ms (network round-trip) to under 5 ms for typical search queries on the 800-table reference dataset. Two files are used:

Security model

Push-down SQL authorization

Permission enforcement happens inside the SQL engine, not in Python. Every user-facing query that returns tables JOINs tables_metadata with permissions_cache WHERE principal IN ($user_groups). Rows for tables the user is not authorized to see are excluded before they reach the application layer.

The sentinel value SELECT_ALL_USERS in permissions_cache.principal marks publicly accessible tables. These rows appear in search results for all authenticated users regardless of group membership.

The _to_duckdb_sql() function ensures parameter substitution is correctly translated between backends. Named parameters in Databricks SQL (%(name)s) are converted to positional parameters (?) for DuckDB, preserving the parameterized-query pattern in both modes and avoiding SQL injection via concatenation.

Feature-level access control

  • EDITOR_GROUPS: comma-separated group IDs allowed to save business name overrides and table metadata edits.
  • ADMIN_GROUPS: comma-separated group IDs allowed to access the admin dashboard and audit logs. There is no demo bypass for admin access.
  • PIPELINE_GROUPS: comma-separated group IDs whose members can trigger and cancel pipeline runs.

Every write function (create_post, delete_post, trigger_pipeline, cancel_run, set_editing_enabled, save_business_name, save_table_metadata) re-checks is_admin() / is_pipeline_user() at the function boundary and raises PermissionError on failure — defense-in-depth beyond the UI gate.

Both dd-app and dd-sync-worker pods run with readOnlyRootFilesystem: true. A /tmp emptyDir volume provides writable scratch space for Streamlit and DuckDB without relaxing the root constraint. User-supplied display names are HTML-escaped at point of use. SMTP headers are sanitized to prevent header injection in comment notification emails.

Entra groups overage

When an Entra user belongs to more than ~150 security groups the ID token omits the inline groups claim and adds _claim_names.groups pointing at Microsoft Graph. src/auth_graph.py detects this shape and calls POST /v1.0/me/getMemberObjects {"securityEnabledOnly": true} to fetch the transitive list, paginated and capped at 50 pages.

Results are kept in a process-level cache (per user OID, 1 h TTL, lock-protected) so they survive across browser tabs. Failure modes (Graph 4xx/5xx, network) return an empty list and log a warning — fail-closed. Admins can flush every cached entry from the admin page; sign-out also drops the user's entry so "sign out, sign back in" picks up new groups immediately. See ADR 006.

Personalisation persistence

User personalisation data (bookmarks, recently viewed tables, column bookmarks) is stored in the user data DuckDB file (USER_DATA_PATH). This file is append-only from the app's perspective and is never modified by the sync job.

The user is identified by their Entra ID Object ID (oid claim), stored as user_oid on every preference row. Preferences are loaded into st.session_state at session start via _sync_prefs_to_session() and written back immediately on user action through _pref_upsert() / _pref_delete().

streamlit — >=1.50,<2 (installed: 1.57.0)

What it does. Streamlit is the web UI framework for the entire application. It renders pages, manages session state, and handles the WebSocket connection between the browser and the Python process. Every tab, card, button, and input in the app is a Streamlit widget. app.py is the single entry point; all pages are sub-modules under src/ui/ and src/pages/ that Streamlit calls on each interaction.

Why it was chosen. The Business Data Dictionary is an internal tool for non-technical business users whose primary interactions are search, browse, and occasional low-frequency writes (bookmarks, comments, metadata edits). The team building it is small with strong Python skills and limited frontend experience. The alternatives considered were:

  • FastAPI + React — full control over the UI and standard HTTP semantics, but requires maintaining two codebases (Python API + JavaScript frontend), adds React state management and build tooling overhead, and adds weeks to the time-to-first-demo.
  • Dash — Python-native like Streamlit but oriented toward data visualization dashboards, not search-first catalog UIs. Less community momentum at time of decision. Streamlit's single-codebase model means the same engineers who write the DuckDB queries write the UI. OIDC authentication, permission enforcement, and search are all expressed in one language. A new tab or feature card is tens of lines of Python rather than coordinated frontend + backend changes. (ADR 003) Known trade-offs.
  • Streamlit drives interactions over a binary WebSocket protocol (protobuf), not plain HTTP. Conventional HTTP load-testing tools (k6, wrk) cannot exercise real user interactions — only the page-shell delivery endpoint. This is mitigated in tests/load/locustfile.py via a DuckDBQueryUser class that exercises the actual performance-sensitive path (the DuckDB search query) directly, bypassing the WebSocket layer.
  • Streamlit re-runs the entire script top-to-bottom on every interaction. Redundant DuckDB queries are avoided through st.session_state caching and by pulling get_authorized_tables() once at the top of render_search_page().
  • Multi-page routing uses a single app.py entry point (not Streamlit's file-based pages/ directory) because tab visibility is permission-aware — some tabs are only shown to ADMIN_GROUPS or PIPELINE_GROUPS members, which requires custom routing logic.
  • Full end-to-end click-flow testing requires Playwright. streamlit.testing.v1.AppTest (used in tests/test_app.py and others) covers rendering and session-state assertions but does not simulate real browser WebSocket interactions.

    What it does. DuckDB is an embedded, in-process columnar analytical database. It runs as a library inside the Python process — no server, no network socket, no daemon. The nightly sync job writes the entire catalog snapshot to a local .duckdb file; the Streamlit app opens that file read-only and executes all search, filter, and aggregate queries against it. The alternatives considered were: - SQLite — built into Python, zero dependency, but designed for transactional OLTP workloads. Multi-table GROUP BY and JOIN queries (the core patterns of a search-and-filter catalog UI) are measurably slower on SQLite than on a columnar engine. No native Parquet export.

  • Not a networked database. Horizontal scaling (multiple Streamlit replicas) requires all pods to share the same PVC mount, which is why dd-data uses ReadWriteMany access mode.

ADR 001 — DuckDB as the local metadata cache

Status: Accepted Date: 2026-04-30 Deciders: Platform team

Context

The nightly sync job crawls Unity Catalog and must store the results somewhere the Streamlit app can query quickly. The catalog has approximately 800 tables; each table has on average 15 columns. The permissions_cache table contains roughly 3 000 rows (one per table-group-privilege triple). Total dataset size is small (well under 100 MB uncompressed).

The query patterns are:

  • Full-text search across tables_metadata and columns_metadata with a JOIN to permissions_cache to enforce row-level security
  • Point lookups by full_name for the table detail panel
  • Aggregate queries for the health dashboard (count of documented tables, column coverage percentage)
  • Occasional UNION queries for related-table discovery The app is read-heavy. A single sync job is the only writer; the app never modifies catalog data (only the user data file). Concurrent read access from multiple Streamlit processes must work without coordination.

    Alternatives considered

    SQLite
  • Built into Python, no additional dependency
  • Familiar to most contributors
  • Analytical queries (aggregates, multi-table JOINs) are notably slower than columnar engines on this workload
  • No native Parquet or CSV export
  • Not designed for analytical access patterns Redis
  • Excellent for key-value lookups (e.g. point lookups by full_name)
  • Requires a running server, adding operational complexity for local development
  • Does not support SQL JOINs natively — permission enforcement would have to move into Python, breaking the push-down security model
  • Overkill for an 800-table catalog; memory overhead is significant Polars in-memory
  • Very fast for analytical queries
  • No persistence — data must be reloaded on every Streamlit session start (cold start penalty of several seconds for 800 tables)
  • No SQL interface — queries must be rewritten in the Polars expression API, diverging from the Databricks SQL strings already tested

Decision

Use DuckDB as the local metadata cache.

DuckDB is an embedded, columnar analytical database that runs in-process (no server required). It speaks SQL, supports parameterized queries, and can read and write Parquet files natively. The duckdb Python package is a single binary wheel with no system dependencies.

Key properties that make it the right fit:

  • Analytical queries with GROUP BY, multi-table JOINs, and UNION run in single-digit milliseconds on the ~800-table dataset (p95 < 8 ms in load testing at 300 concurrent users)
  • The same SQL strings used against the Databricks SQL Warehouse work against DuckDB after minor dialect translation (handled by _to_duckdb_sql())
  • The catalog file is a single .duckdb file that the sync job replaces atomically with os.replace(). Readers that have the old file open continue to see a consistent snapshot; new readers pick up the replacement on next open
  • The user data file (dict_user_data.duckdb) is ATTACHed at runtime, enabling cross-file JOINs without any server coordination
  • Local development requires no infrastructure: set DUCKDB_PATH and DEMO_DATA=true, run streamlit run app.py

Consequences

Positive:

  • Sub-10 ms search queries in the read path, regardless of Databricks SQL Warehouse availability
  • Zero infrastructure dependency for local development and CI
  • Single-file portability: the entire catalog snapshot can be copied, backed up, or inspected with any DuckDB client Negative:
  • DuckDB enforces a single-writer constraint per file. The sync job holds an exclusive write lock while rebuilding the catalog file. During a sync (typically 30–90 seconds) the app falls back to the previous file via the atomic-replace mechanism. The transition window is safe but operators should be aware of it.
  • The _to_duckdb_sql() dialect translator adds a small maintenance surface. New query patterns that use Databricks-specific functions must be added to the translator when DuckDB support is needed.
  • DuckDB is not a networked database. Horizontal scaling (multiple app replicas) requires that all replicas share the same PVC mount point. This is the reason the PVC uses ReadWriteMany access mode. On clusters without a shared filesystem, this constraint must be addressed at the storage layer.

ADR 002 — Push-down SQL for permission enforcement

Status: Accepted Date: 2026-04-30 Deciders: Platform team, Security team

Context

The catalog contains tables owned by different business units. Users must only see tables they are authorized to access. Authorization is modeled as a set of Entra ID Security Group Object IDs extracted from the groups claim in the user's OIDC token.

The sync job extracts every GRANT from Unity Catalog and writes one row per (table, principal, privilege) triple into permissions_cache. At query time, the app knows the user's group IDs. The question is: where should the permission check happen?

Option A — Python-side filtering

  1. Run the search query without any permission filter, retrieving all matching rows
  2. In Python, filter the result set to only include tables where permissions_cache.principal overlaps with the user's groups Problems:
- The full result set is fetched from the database before filtering. For broad queries this means sending potentially thousands of unauthorized rows across the connection.
  • If a bug is introduced in the Python filter, unauthorized rows can leak to the user interface. The defense is a single point of failure.
  • Pagination and row counts become incorrect (the total count before filtering does not match the count after filtering).
  • It is impossible to express "how many results exist for this user" without reading all results first.

    Option B — Push-down SQL JOIN

    Enforce permissions by requiring every user-facing query to JOIN tables_metadata with permissions_cache WHERE principal IN ($user_groups). The database engine discards unauthorized rows before returning any data. The sentinel value SELECT_ALL_USERS in permissions_cache.principal marks tables that are publicly accessible to all authenticated users. A query that includes SELECT_ALL_USERS in the IN list returns those rows for everyone.

Decision

Use push-down SQL authorization. All queries that return table-level results must include the permissions JOIN. The application layer performs no secondary filtering.

Implementation:

SELECT
    t.full_name,
    t.description,
    t.table_type
FROM tables_metadata t
JOIN permissions_cache p
    ON p.full_name = t.full_name
WHERE p.principal IN (%(group_1)s, %(group_2)s, 'SELECT_ALL_USERS')
  AND t.full_name ILIKE %(query)s
GROUP BY t.full_name, t.description, t.table_type

Parameterized queries are used throughout. The _to_duckdb_sql() function translates named parameters (%(name)s) to positional parameters (?) for DuckDB, preserving the parameterized pattern in both backends and preventing SQL injection via concatenation.

Consequences

Positive:

  • Unauthorized rows are never returned from the query engine. There is no Python code path that could accidentally expose them.
  • Row counts and pagination are correct from the first query.
  • The approach is transparent to auditors: every logged SQL statement is self-contained and shows exactly which groups were used.
  • Works identically against DuckDB (local) and Databricks SQL Warehouse (production). Negative:
  • Every search query must include the permissions JOIN, adding complexity to query construction and making the SQL harder to read in isolation.
  • The IN clause for group IDs can become long if a user belongs to many groups. DuckDB and Databricks SQL both handle large IN lists efficiently, but this is a theoretical concern for organizations with very deep AD group nesting.
  • The SELECT_ALL_USERS sentinel is a convention, not a database constraint. If the sync job stops writing it for public tables, those tables silently disappear from all user views. This must be guarded by integration tests in the sync job.
  • Query logic must not be bypassed. Any new query that returns table metadata must include the JOIN. Code review must enforce this; there is no automated check yet.

  • Table detail (click a result, see columns, grants, lineage, comments)
  • Glossary browsing
  • Bookmarking and commenting (low-frequency writes) The team building the tool is small (two to three engineers) with strong Python skills and limited frontend experience. Time-to-first-demo was a key constraint: the tool needed to be usable by business stakeholders within two weeks of the decision to build it.

    Option A — FastAPI + React

    A REST or GraphQL API in FastAPI with a React (or Next.js) frontend. Advantages:
  • Full control over the UI — any design system, any interaction pattern
  • Standard HTTP semantics enable conventional load testing tools (k6, wrk, Gatling)
  • Stateless API is easy to scale horizontally Disadvantages:
  • Requires maintaining two codebases (Python API + JavaScript frontend)
  • React component development, state management (Redux or Zustand), and build tooling add significant overhead for a two-person team
  • Time-to-first-demo is weeks, not days
  • API authentication (session tokens, CSRF, CORS) requires explicit implementation
  • CI must cover both Python and JavaScript test suites

    Option B — Streamlit

    A single Python file that defines both the UI and the business logic. Streamlit handles the WebSocket connection, session state, and server-side rendering. Advantages:
  • Single Python codebase. The same team that writes the data pipeline writes the UI.
  • Rapid iteration: adding a new tab or card is tens of lines of Python
  • Built-in session state management removes the need for external state stores
  • OIDC authentication is implemented once in Python; no separate frontend auth concern
  • Existing Streamlit AppTest framework enables pytest-based integration tests without a browser Disadvantages:
  • Interactive features (button clicks, widget state) are driven over a binary WebSocket protocol (protobuf). Conventional HTTP load testing tools cannot exercise real interactions — only the page-shell HTTP endpoint is testable with tools like Locust's HTTP user class.
  • The workaround for load testing is to test the query layer directly (DuckDB reads) using a separate DuckDBQueryUser class in Locust. This reflects the actual performance-sensitive path: DuckDB search queries, not HTTP page delivery.
  • Multi-page routing (Streamlit's file-based pages/ directory) was not used because the app has a custom tab navigation model with permission-aware tab visibility. A single entry point (app.py) is simpler to reason about for this use case.
  • app.py grows large without discipline. The refactoring roadmap (REFACTORING.md) addresses this by extracting modules into src/.

Decision

Use Streamlit for the initial version of the Business Data Dictionary.

The business user audience, small team size, and rapid-iteration requirement favor a Python-native approach over a two-tier web architecture. The WebSocket interaction model is a known limitation for HTTP load testing, which is mitigated by testing the DuckDB query layer directly.

A migration to FastAPI + a lightweight frontend remains a valid long-term option if the team grows or if more complex UI interactions are required, but is out of scope for v0.x.

Consequences

Positive:

  • Single Python codebase with pytest integration tests
  • New screens can be added in hours, not days
  • OIDC auth, permission enforcement, and DuckDB queries are all in one language Negative:
  • Full end-to-end interaction testing requires Playwright or a similar browser automation tool; pytest AppTest covers rendering but not real click flows
  • HTTP load testing (Locust DictionaryHTTPUser) tests only page delivery, not the actual app logic. The DuckDBQueryUser in tests/load/locustfile.py fills this gap by directly executing the search SQL that the app would run
  • Streamlit's execution model (top-to-bottom re-run on every interaction) requires careful use of st.cache_data and st.session_state to avoid redundant database queries
  • app.py at 4 000+ lines is currently a monolith. Extraction to src/ modules is tracked in REFACTORING.md

ADR 004 — Sidecar sync worker

Status: Accepted Date: 2026-05-07 Deciders: Platform team

Context

The Streamlit app needs to push column-definition edits, audit events, comments, and other user-authored changes back to Databricks Unity Catalog. Until now this was done by an in-process daemon thread started from app.py:

# Old approach — src/sync/worker.py (now removed)
@st.cache_resource(show_spinner=False)
def _start_sync_worker_thread():
    t = threading.Thread(target=_loop, daemon=True)
    t.start()
    return t

Three problems with this design surfaced in the May 2026 audit:

  1. Shared DuckDB connection. _get_shared_duckdb_connection() returns a single in-memory DuckDB connection cached via @st.cache_resource. The worker thread, every Streamlit script-runner thread, and the DR resync code all called execute() on it concurrently. DuckDB connections are not safe for concurrent execute calls — only writes were guarded by _db_write_lock; reads collided freely. Symptoms: intermittent Connection was closed errors and silently stale reads. 2. Streamlit cache from a non-Streamlit thread. The worker thread had no ScriptRunContext. Calling @st.cache_resource-decorated functions from a thread without a ScriptRunContext is undefined behaviour and varies between Streamlit minor versions. 3. Two _LAST_UI_ACTIVITY state objects. The same set of helpers (_get_last_ui_activity, _mark_ui_activity, _get_dr_resync_status) was duplicated in src/sync/worker.py and src/ui/cards.py, each with its own _worker_state_lock. app.py imported _mark_ui_activity from both modules; the second import won. Net effect: the UI ticked the cards.py copy, the worker read the worker.py copy, so the worker was effectively always in idle mode and used the high-throughput batch size unconditionally. Subtle but real. A fourth latent issue: src/sync/push.py referenced last_attempt_at
in an UPDATE, but the column was never declared in _initialize_schema(). Every optimistic update threw silently and the queue stalled.

Decision

Move the drain loop and DR resync into a separate process running python -m src.sync.daemon. Streamlit pods only enqueue into user_data.pending_sync; the daemon is the sole pusher.

Process boundary

ResponsibilityStreamlit podsSync worker
Enqueue into pending_sync✓—
Write user overrides (business names, comments, audit)✓—
Drain pending_sync → Databricks—✓
DR resync (Databricks → local)—✓
Stale-row recovery—✓
Heartbeat / status to site_settings—✓

Connection ownership

  • Streamlit pods continue to use _get_shared_duckdb_connection() (Streamlit-cached, in-memory, ATTACHes the catalog file read-only and the user_data file read-write).
  • The daemon uses src.sync.daemon_db.DaemonConn — a process-local DuckDB connection with no Streamlit cache. Same shape as _DuckDBConn so _process_sync_queue and run_dr_resync accept either.

    IPC

    The pending_sync table is the queue — no Redis, no RabbitMQ, no message
broker. The DuckDB OS-level file lock serialises writes from the Streamlit enqueue path and the daemon's drain updates. The daemon writes status keys (worker_heartbeat, dr_resync_status) into user_data.site_settings; the UI reads them via src.sync.worker.read_dr_resync_status().

Health and recovery

  • HTTP GET :8765/healthz returns 200 if a heartbeat was written within SYNC_HEALTHZ_TIMEOUT_S (default 60s), else 503 — used by the k8s liveness probe.
  • Stale-row recovery at the top of every cycle: rows in 'syncing' state with last_attempt_at < now - SYNC_STALE_ROW_S (default 300s) flip back to 'pending'. A daemon crash mid-push therefore can't lock rows permanently.
  • SIGTERM sets _stop_event; the current cycle finishes (max ~30s with terminationGracePeriodSeconds: 60) and the daemon exits cleanly.

    Deployment

    Singleton — replicas: 1 with strategy: Recreate. Sharing dd-data
PVC with dd-app. Runs the same image with command: overridden.

Alternatives considered

Keep the in-process daemon

  • Cheapest in lines of code.
  • Fails the concurrency review: shared DuckDB connection across threads is undefined; Streamlit's threading guarantees don't extend to caches used from non-script-runner threads.
  • Hides the failure: most edits succeed, occasional ones throw silently, the queue accumulates, nobody notices until the queue table is large.

    Per-replica writer

    Run a sync thread inside each Streamlit replica. Each opens its own
DuckDB connection and competes for the OS lock.
  • Doesn't solve the Streamlit-context-from-thread problem.
  • N replicas all drain the same queue → race conditions on the 'pending' → 'syncing' transition unless we add row-level claiming.
  • Hard to reason about which replica is doing what.
  • No clear separation between "user-facing pod" and "background work".

    External queue (Redis Streams / RabbitMQ / Azure Service Bus)

    Replace pending_sync with a managed queue. - Best long-term option — provides at-least-once delivery, retry backoff, observability.
  • Operational overhead: another moving part to deploy, monitor, secure, rotate credentials for.
  • Out of proportion for current write volume (≤100 ops/min).
  • Adds latency for the visible "edit applied" feedback loop in the UI.
  • Revisit if the team is already running Redis or Service Bus for other reasons.

    Cron-style one-shot pod

    Replace the long-lived daemon with a CronJob running
python -m src.sync.daemon --once every minute.
  • Simpler deployment shape.
  • Cold-start cost on every run (DuckDB connection setup, Databricks auth) — at 1 run/min, ≥30% of the cycle is overhead.
  • DR resync cadence becomes locked to the cron interval; the long-lived daemon can run DR resync on a different cadence (every Nth cycle).
  • Stale-row recovery is harder when each invocation is independent — who owns the lifecycle of a row stuck in 'syncing'? The CronJob shape is reasonable for environments where running
long-lived pods is forbidden. We may add it as an alternate deployment mode if needed; for now the long-lived Deployment wins.

Consequences

Positive:

  • DuckDB shared-connection concurrency bugs are gone — Streamlit and the daemon never touch the same Python connection object.
  • The daemon is now testable in isolation. tests/test_sync_daemon.py exercises the loop, stale-row recovery, healthz, and DR resync with a fake _databricks_query. Previously the loop was a while True inside a thread inside a @st.cache_resource — effectively impossible to unit-test.
  • One source of truth for sync status. The UI reads from user_data.site_settings; the daemon writes there. No more duplicated _LAST_UI_ACTIVITY state.
  • Streamlit pods become stateless w.r.t. background work. Restarting dd-app no longer restarts the sync worker; rolling out a new image doesn't restart drains in flight. Negative: - Two Deployments to operate instead of one. Documented in docs/runbooks/sync-worker.md.
  • DuckDB still has multiple writers (Streamlit pods + daemon). Today the OS file lock serialises them and write volume is low enough that it doesn't matter. If write contention surfaces under load, migrate user_data to PostgreSQL — tracked in TODO.md.
  • The UI no longer shows "Active vs Idle mode" because the daemon doesn't track UI activity any more. We replaced that panel with "Worker heartbeat" + "Self-Healing (DR)" — more accurate, less decorative. Out of scope: - Multi-writer support beyond DuckDB's lock-serialised default.
  • Replacing pending_sync with a managed queue.
  • Replacing the long-lived Deployment with a CronJob.

ADR 005 — Per-entity storage abstraction

Status: Accepted Date: 2026-05-08 Deciders: Platform team

Context

Before this change, every entity persisted by the app (src/cms.py, src/pipelines.py, src/personalization.py, src/audit.py) carried its own copy of the same three-way switch:

def get_active_posts():
    if not _duckdb_available():
        # session-state path
        ...
        return ...
    try:
        # DuckDB path
        ...
    except Exception as exc:
        log.warning("Could not load CMS posts: %s", exc)
        return []

The same pattern repeated ~13 times across four files. Adding a fifth entity (e.g. comments, glossary edits) would have meant writing it again. Two specific costs:

  1. Duplicated bug surface. Two of the four modules had subtly different exception-handling shapes; a fix to one didn't automatically reach the others.
  2. Tests were brittle. Most existing tests mocked _duckdb_available to False to force the demo path, which coupled tests to the runtime-routing implementation. Renaming or refactoring the routing function broke unrelated tests. A senior-developer audit (TODO #4) recommended a Protocol-based
storage abstraction with one factory per entity.

Alternatives considered

A single Storage god-class with everything on it. Tempting because there's only one factory call site. But it conflates unrelated entities — adding a CMS field would force every test that imports Storage to update mocks, even tests in unrelated modules. Worse, the "Databricks" backend implementation differs per entity (CMS has no Databricks variant; audit has both DuckDB and Databricks), forcing the god-class to be either an empty-method base or a fat-interface anti-pattern. Rejected.

abc.ABC instead of typing.Protocol. Explicit class DuckDBCMSStorage(CMSStorage) is more discoverable in IDEs but forces every test fake to inherit from the same ABC. Tests already had ad-hoc fakes inline — keeping them as plain classes that satisfy a structural Protocol let us migrate one entity at a time without rewriting fakes. Rejected.

A repository / unit-of-work pattern with explicit transactions. Real ORMs need this; we don't. DuckDB writes are already serialised by _db_write_lock, and the session-state backend has no concept of a transaction. Adding the layer would be all overhead. Rejected.

Status-quo: keep the duplicated branches. Accepted technical debt for as long as the entity count stayed small. At four entities and 13 duplicated branches, the cost-benefit flipped.

Decision

Per-entity Protocols, each with one or more concrete backends. Factory functions in src/storage/__init__.py pick the backend at call time based on is_demo_mode() and _duckdb_available().

Layout

` src/storage/ __init__.py factories: get__storage() cms_storage.py CMSStorage — Demo / DuckDB / Fake pipeline_storage.py PipelineDefStorage — Demo / DuckDB / Fake PipelineRunStorage — Demo / DuckDB / Fake preference_storage.py PreferenceStorage — Demo / DuckDB / Fake SiteSettingStorage — Demo / DuckDB / Fake audit_storage.py AuditStorage — Demo / DuckDB / Fake BusinessNameOverrideStorage — Demo / DuckDB / Fake `

Conventions

  • Protocols are runtime-checkable so tests can do isinstance(x, CMSStorage) smoke tests for protocol coverage.
  • Demo backends mirror the previous session-state behaviour literally (no behavioural change); Site_Setting and Preference demo backends are intentional no-ops to preserve pre-refactor behaviour where the in-process session cache was the only runtime-mutable knob without DuckDB.
  • Fake backends are session-free in-memory dicts; they don't depend on Streamlit and are usable from any unit test via mock.patch("src..get__storage", return_value=fake).
  • Factories are not cached. is_demo_mode() and _duckdb_available() re-evaluate per call so tests can flip env vars between calls and see consistent behaviour. Cost is microseconds.
  • The wrapper module (src/cms.py, etc.) keeps its public API identical so callers don't change. New code can import the storage directly if it needs Protocol-typed access.

    Test pattern

    Before:
@patch("src.cms._duckdb_available", return_value=False)
def test_create_post(mock):
    create_post(...)
    assert st.session_state["_demo_cms_posts"] == [...]

After: 

def test_create_post():
    fake = FakeCMSStorage()
    with patch("src.cms.get_cms_storage", return_value=fake):
        create_post(...)
    assert fake.posts[0]["title"] == "Hello"

The new shape decouples the test from the routing implementation.

Direct-Databricks variants removed (TODO #7)

DatabricksAuditStorage and DatabricksBusinessNameOverrideStorage were initially added alongside the Demo / DuckDB pair so the app could fall back to the SQL Warehouse when DuckDB was missing. After the sidecar daemon (ADR 004) became the only intentional Databricks writer, those classes were dead code — every Streamlit pod has DuckDB locally in production, and writes go through the queue. They were deleted in TODO #7 along with _get_databricks_write_connection. _get_write_connection now raises a clear error if DuckDB is unavailable instead of silently opening a fresh SQL Warehouse session per write.

Consequences

Positive:

  • Adding a new entity is a recipe, not a question: 1. Define Storage(Protocol). 2. Implement DemoStorage, DuckDBStorage, FakeStorage. 3. Add a get__storage() factory. 4. Replace the wrapper module's body with one-liners.
  • 13 duplicated branches collapsed to ~50 lines of routing logic.
  • Tests inject Fake*Storage rather than mocking _duckdb_available, which decoupled them from the runtime-routing implementation. Negative: - One more module to read for a contributor doing their first entity-level change. Mitigated by the regularity — once you've read one storage module, you've read them all.
  • Protocol-based typing has weaker IDE support than ABC inheritance in some editors. Hasn't been a problem in practice. Out of scope: - A CommentStorage for src/comments.py. The pattern is the same; migration is mechanical. Deferred to a future ticket if the entity grows new fields.
  • Migrating src/pages/search.py from src.db.queries.get_column_business_names to BusinessNameOverrideStorage.get_for_table. Mechanical follow-up.

ADR 006 — Entra ID groups overage handling

Status: Accepted Date: 2026-05-08 Deciders: Platform team, Identity team

Context

Authorisation in this app is push-down SQL: the permissions_cache table stores one row per (table, principal, privilege), and every result-returning query joins tables_metadata against permissions_cache WHERE principal IN (user's Entra security groups). The user's group set comes from the groups claim on their Entra ID ID token, which the app reads on sign-in:

st.session_state.user_groups = claims.get("groups", [])

This works for typical users. It silently fails for users with more than ~150 Entra security-group memberships. Microsoft Entra omits the inline groups claim in that case and adds a pointer:

{
  "_claim_names":   { "groups": "src1" },
  "_claim_sources": { "src1": { "endpoint": "https://graph.microsoft.com/..." } }
}

Without explicit handling, claims.get("groups", []) returns [], the join returns no rows, and the user sees zero tables. This is invisible in dev (small group counts) but a hard production failure for enterprise tenants — IT admins, partner teams, anyone with broad group membership.

A senior-developer audit (TODO #2) flagged this as a critical production-failure mode worth fixing immediately.

Alternatives considered

Reduce Entra group emission to security-enabled-only. Entra has a token configuration option that only emits security groups, raising the overage threshold. Helps but doesn't eliminate the class of failure: tenants with >150 security groups (large enterprises) still hit it. And it's a tenant-wide setting, not something an app can rely on. Rejected as a sole solution.

Switch the auth model to per-table grants in the app's own DB. Move authorisation out of Entra entirely and maintain our own permission store. Far too invasive for the problem at hand and abandons the "Entra is the source of truth" principle the app was built on. Rejected.

Read the access token's groups claim instead of the ID token. Same overage limit applies. Rejected.

Document the limit and tell affected users to reduce their group count. Not viable — a user can't reduce their own group count, and IT admins can't either without security review.

Decision

Detect the overage shape in check_auth and call Microsoft Graph's getMemberObjects to fetch the transitive security-group list using the access token MSAL has already produced.

Detection

src.auth_graph.has_groups_overage(claims) returns True iff:

"groups" not in claims and "groups" in (claims.get("_claim_names") or {})

Both conditions matter. A token with both inline groups and a _claim_names entry (rare, but possible) still uses the inline list.

Resolution

When overage is detected, _resolve_user_groups calls fetch_member_groups(access_token, user_oid):

`http POST https://graph.microsoft.com/v1.0/me/getMemberObjects Authorization: Bearer Content-Type: application/json

{"securityEnabledOnly": true} `

Response is paginated via @odata.nextLink — first page is POST, subsequent pages are GET against the absolute URL Graph returns. The implementation caps pagination at 50 pages so a buggy server can't loop forever. With the default 11 000-IDs-per-call from Graph that's plenty.

Caching

Results are cached in a process-level dict keyed by user OID with a 1 h TTL. Lock-protected because Streamlit's script-runner threads can call into the cache concurrently.

@st.cache_data was deliberately rejected — it's session-scoped, so each browser tab would force a fresh Graph call. For a feature that exists to handle "this user is in many groups" that's exactly the wrong default.

Failure modes

Any error (network, 4xx including 403, 5xx) returns [] and logs a warning. The user sees no tables. We never silently grant access by returning a wider set on failure — fail-closed is the only correct default for an authorisation layer.

Cache invalidation

Two triggers:

  1. Sign-out drops the user's cache entry (_clear_auth_session calls clear_groups_cache(user_oid)). Without this, "sign out and sign back in" would still read 1 h-stale group memberships and defeat the user's instinct for fixing access issues. 2. Fresh OIDC code-exchange clears the cache for the new user OID before resolving groups, so a successful sign-in always reflects current Entra state regardless of whether the previous session was signed out cleanly. 3. Admin button (§ Group permissions cache → Flush groups cache) drops every cached entry. Use case: an admin grants a user a new group, the user is still signed in, the admin clicks the button, the user reloads and sees the new tables.

    Required scope

    SCOPE in src/config.py includes GroupMember.Read.All. This was
already in the scope list before this ADR but was load-bearing only once we added the Graph call. Removing it would break overage users — documented inline in src/config.py so future readers don't think it's safe to drop.

Consequences

Positive:

  • Affected users (>150 groups) now see the catalog. Before this, they saw zero rows with no error message and no clear path to a fix.
  • The cache invalidation invariants (sign-out, sign-in, admin flush) give admins three predictable ways to refresh permissions, all documented in the runbook and CLAUDE.md.
  • Tests cover overage detection, pagination, all failure modes, cache hit/miss, and the three cache-clear paths. Negative: - One Microsoft Graph call per affected user per cache TTL — small cost. getMemberObjects returns up to 11 000 IDs per page; the cache amortises the cost across all renders for that user in the next hour.
  • Pagination cap (50 pages, 550 000 IDs) is far above any real-world ceiling. If exceeded the daemon logs a warning and truncates; the user sees a subset of their groups. Acceptable given the contrived threshold.
  • The admin "Flush groups cache" button affects every active user, not one. This is intentional — admins normally don't know which user needs the refresh, and the cost (one Graph call per active user on next render) is bounded. Out of scope: - SSO logout / forced silent re-auth on group-membership change. Group changes propagate at the next token refresh (≤1 h) plus the cache TTL (≤1 h). Combined with the explicit invalidation triggers above, the worst case is ~1 h delay; tighter latency would require webhooks or polling Graph, neither of which is justified at current scale.
  • Pre-computing group lists at sync time. Group membership is a per- user concern at request time, not a property of the catalog data — caching it cluster-wide doesn't help.

Common operations

Restart after a config change

Recreate rollout strategy (single writer, no overlap):

kubectl -n data-dictionary rollout restart deploy/dd-sync-worker
kubectl -n data-dictionary rollout status deploy/dd-sync-worker --timeout=60s

Drain the queue manually

If the worker is failing repeatedly and the queue is backing up, you can mark all pending rows as failed to stop the retry storm and inspect them out of band:

UPDATE user_data.pending_sync
   SET status = 'failed',
       last_error = 'manually drained'
 WHERE status IN ('pending', 'syncing');

Then fix the underlying issue, re-enqueue from the audit log, and let the daemon resume.

Force a DR resync

Either bounce the pod (the first cycle always runs DR resync), or set the counter to a multiple of SYNC_DR_EVERY_N by waiting it out.

Failure modes

/healthz returns 503 with heartbeat_age_s: null

The daemon never wrote a heartbeat. Almost always a startup error — DUCKDB_PATH unset, file permissions on /data, or a parse error in the schema migration. Check the pod logs.

/healthz returns 503 with heartbeat_age_s: 9999

The daemon is alive but stuck. Check logs for the most recent Daemon cycle error: entry. If _recover_stale_rows is failing the whole cycle aborts. Common causes: catalog file corruption (rare; check PVC), or a Databricks auth failure that throws inside DR resync (the loop catches this but logs ERROR — confirm token freshness).

dr_resync_status stuck on Error: …

Read the full error from logs. If transient (network blip), the next cycle will retry. If persistent (auth, schema mismatch), the daemon is otherwise healthy — pending_sync drain still happens on every cycle.

Pending queue grows unbounded

Indicates one of:

  1. Databricks creds are wrong or expired → all pushes fail, attempts counter increments. After _SYNC_MAX_ATTEMPTS (3) rows go to 'failed' and stop retrying.
  2. The daemon is crashing every cycle → check liveness probe events.
  3. The schema in Databricks doesn't match what the push expects → look at last_error on a stuck row. 
    SELECT sync_type, count(*), max(last_error) FROM user_data.pending_sync WHERE status IN ('pending', 'failed') GROUP BY sync_type;

    Two writers contention (DuckDB OS lock)

    Multiple processes write to USER_DATA_PATH: the sync worker and the
Streamlit pods (which enqueue and write user overrides). DuckDB serialises them via an OS-level file lock. At low write volume (typical for this app) you'll never notice. If write contention shows up under load the fix is migrating user_data to PostgreSQL — tracked in TODO.md.

Secret rotation runbook

Procedure for rotating credentials stored in the dd-app-secrets Kubernetes Secret without downtime. The rolling update strategy (maxUnavailable: 0) ensures at least one pod stays healthy throughout.

All commands assume kubectl is configured for the target cluster and your shell context is set to the correct namespace, or you append -n data-dictionary explicitly.

1. Rotate the Databricks PAT token

When to do this

  • Quarterly as a matter of policy
  • Immediately if the token is suspected to be compromised
  • When the token expires (PATs have a configurable TTL in Databricks)

    Steps

    1. Generate a new PAT in the Databricks workspace UI under Settings > Developer > Access tokens. 2. Base64-encode the new token: bash echo -n '' | base64 3. Patch the secret in place (no pod restart required at this step): bash kubectl patch secret dd-app-secrets \ --namespace data-dictionary \ --type='json' \ -p='[{"op":"replace","path":"/data/DATABRICKS_TOKEN","value":""}]' 4. Trigger a rolling restart so pods pick up the new value: bash kubectl rollout restart deployment/dd-app -n data-dictionary 5. Watch the rollout complete: bash kubectl rollout status deployment/dd-app -n data-dictionary 6. Verify the new token works by tailing a pod's logs and confirming no auth errors: bash kubectl logs -n data-dictionary -l app=dd-app -f --max-log-requests=2 7. Revoke the old token in the Databricks UI.

2. Rotate the Entra ID client secret

When to do this

  • When the secret is approaching its expiry date (check in Azure Portal > App registrations > Certificates & secrets)
  • Immediately if the secret is suspected to be compromised

    Steps

    1. In Azure Portal, navigate to your app registration and create a new client secret. Copy the Value (it is only shown once). 2. Base64-encode the new secret: bash echo -n '' | base64 3. Patch the Kubernetes secret: bash kubectl patch secret dd-app-secrets \ --namespace data-dictionary \ --type='json' \ -p='[{"op":"replace","path":"/data/CLIENT_SECRET","value":""}]' 4. Restart the deployment: bash kubectl rollout restart deployment/dd-app -n data-dictionary kubectl rollout status deployment/dd-app -n data-dictionary 5. Test the OIDC login flow end-to-end by signing in as a test user. 6. Delete the old secret from the Azure Portal app registration.

3. Rotate the GHCR image pull secret

When to do this

  • When the GitHub personal access token (PAT) used for GHCR access expires or is revoked
  • When rotating PATs as part of a broader credential hygiene exercise

    Steps

    1. Generate a new GitHub PAT with read:packages scope at GitHub > Settings > Developer settings > Personal access tokens. 2. Delete the existing pull secret: bash kubectl delete secret ghcr-pull-secret -n data-dictionary 3. Recreate it with the new token: bash kubectl create secret docker-registry ghcr-pull-secret \ --namespace data-dictionary \ --docker-server=ghcr.io \ --docker-username= \ --docker-password= 4. The secret is read at image-pull time, so a restart is only needed if the current pods are crash-looping due to ImagePullBackOff. In steady state, existing pods are unaffected: bash kubectl get pods -n data-dictionary -l app=dd-app 5. Confirm new pods (triggered by the next deploy) can pull the image: bash kubectl describe pod -n data-dictionary -l app=dd-app | grep -A5 "Events"

Verification checklist

After any secret rotation, confirm the following before closing the change:

  • [ ] kubectl rollout status deployment/dd-app -n data-dictionary reports successfully rolled out
  • [ ] Pod logs show no authentication errors in the first two minutes after restart
  • [ ] A test search returns results (Databricks / DuckDB connection is live)
  • [ ] OIDC sign-in flow completes without errors (Entra ID rotation only)
  • [ ] Old credential has been revoked in the originating system
