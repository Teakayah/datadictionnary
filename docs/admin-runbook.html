§ 1 — Sync

Sync queue monitoring

The Sidecar sync worker drains user_data.pending_sync and pushes changes to Databricks. The Admin dashboard → Operations tab shows live queue stats. For a high-level summary of the product goals, see the Product Overview.

Reading the sync panel

MetricMeaningNormal range
PendingRows waiting to be processed0–10 under normal load
ProcessingRows currently in flight (status = 'syncing')0–5
DoneSuccessfully pushed to Databricks in this sessionAny
FailedRows that exhausted 3 retry attempts0 — investigate immediately
HeartbeatLast time the sidecar wrote to worker_heartbeat< 60 s ago

Heartbeat stale — worker is down

Symptom: Heartbeat shows > 60 s ago or "Daemon offline". The k8s liveness probe will restart the pod automatically. If it stays offline, check the pod logs. See ADR 004 for architecture details.
  1. Check the sidecar pod status: kubectl get pods -l app=dd-sync-worker
  2. Read logs: kubectl logs deploy/dd-sync-worker --tail=100
  3. Common causes: DuckDB file lock contention, Databricks credential expiry, OOM. Address the root cause. See the Sync Worker Runbook for detailed troubleshooting.
  4. If the pod is in CrashLoopBackOff, check USER_DATA_PATH is correctly mounted and the PVC is healthy.
  5. The worker restores itself on restart — no manual queue intervention needed unless rows are stuck in 'syncing' state.

Failed rows

  1. Failed rows are visible in the sync panel table. Note the object_type and object_name.
  2. Query directly: 
    SELECT * FROM user_data.pending_sync WHERE status = 'failed';
  3. Check the last_error column for the rejection reason from Databricks (most common: invalid identifier, privilege error, or token expiry).
  4. Fix the underlying cause (e.g., re-grant MODIFY on the target table), then reset the row: 
    UPDATE user_data.pending_sync SET status = 'pending', attempt_count = 0 WHERE status = 'failed';
  5. The worker will pick it up on the next poll cycle (default 5 s active, 30 s idle).
§ 2 — Recovery

Stale-row recovery

A row stuck in 'syncing' for more than 5 minutes (configurable via SYNC_STALE_ROW_S) is automatically flipped back to 'pending' at the top of each worker cycle. This handles crashes mid-flight without manual intervention.

Manual recovery (if auto-recovery fails)

  1. Identify stuck rows: 
    SELECT * FROM user_data.pending_sync
WHERE status = 'syncing'
  AND updated_at < NOW() - INTERVAL 10 MINUTES;
  2. Reset them manually: 
    UPDATE user_data.pending_sync
SET status = 'pending'
WHERE status = 'syncing'
  AND updated_at < NOW() - INTERVAL 10 MINUTES;
  3. Confirm the worker picks them up within one poll cycle. Watch the heartbeat timestamp in the Admin panel.
Do not delete rows from pending_sync unless you intentionally want to abandon a change. Deletion bypasses the audit trail.
§ 3 — DR resync

DR resync management

Every 20 worker cycles the sidecar runs a DR resync: it pulls the current audit log, business-name overrides, and table-metadata overrides back from Databricks into the local DuckDB file. This keeps the local cache consistent with the source of truth after a pod restart or PVC swap.

Reading resync status

StatusMeaning
okLast resync completed without errors.
runningResync in progress (completes in seconds under normal load).
errorLast resync failed. Check worker logs for the specific SQL error.
neverWorker has not yet run a resync cycle (normal on first boot).

Force a resync immediately

  1. Run the worker in single-cycle mode: python -m src.sync.daemon --once
  2. Or restart the sidecar pod — it runs a full cycle on startup.
  3. Confirm status changes to ok in the Admin panel within 30 s.

Resync fails repeatedly

  1. Check worker logs for the SQL error. Common causes: Databricks SQL Warehouse offline, token expired, schema version mismatch.
  2. Verify the warehouse is running: open Databricks UI → SQL Warehouses → confirm state is Running.
  3. Check token expiry: kubectl get secret dd-databricks-secret -o yaml and verify DATABRICKS_TOKEN is not expired.
  4. If schema has drifted, run python scripts/nightly_sync.py manually to recreate dictionary_cache tables with the correct schema.
§ 4 — Access control

Group-cache operations

The application caches each user's Entra ID group memberships in process memory for 1 hour (keyed by user OID). This prevents repeated Graph API calls for every page load. The cache is cleared per-user on sign-out. See ADR 006 for detailed identity architecture.

When to flush the cache

  • A user was added to or removed from an Entra group and needs immediate access change (without waiting up to 1 hour).
  • You performed bulk group changes (e.g., during an org restructure) and want all users to see the new state.
  • A user reports seeing tables they should no longer have access to.

Flush via Admin dashboard

  1. Open the Admin tab → Operations → Group cache section.
  2. Click Flush group cache. This clears all cached group memberships for all active users.
  3. Each user's cache is rebuilt on their next page load via a fresh Microsoft Graph API call.
Note for users with 150+ group memberships. These users trigger the Graph API overage path (getMemberObjects). The cache TTL is the same (1 hour), but the first page load after a flush will be slightly slower while Graph resolves their full membership list. See ADR 006.

Manual cache inspection (engineering)

The cache lives in src/auth_graph.py as a module-level dict _groups_cache. In a production context it is process-local and not observable from outside the pod. To inspect it, attach to the running pod:

kubectl exec -it deploy/dd-app -- python -c \
  "from src.auth_graph import _groups_cache; print(list(_groups_cache.keys()))"
§ 5 — Governance

Global editing toggle

Inline editing can be disabled globally without redeploying the application. This is useful during catalog migrations, nightly sync windows, or whenever you need a temporary freeze. For the steward's perspective on editing, see the Steward Guide.

Toggle via Admin dashboard

  1. Open the Admin tab → Operations → Inline editing section.
  2. The current state is shown as Editing enabled or Editing disabled.
  3. Click the toggle. The change takes effect immediately for all users on the next page load — no restart required.
Where the flag lives. The state is stored in user_data.site_settings with key='editing_enabled'. It defaults to True when the row is absent (safe for first boot). The value is cached in each user's st.session_state and refreshed on re-render.

What disabling editing does

  • The edit icon disappears from all table description, steward, and column fields for all power users.
  • Admins retain the ability to approve and reject proposals already in the queue.
  • Existing pending_approval rows are not affected — they remain in the queue.
  • The toggle state is visible in the Admin panel at all times.
§ 6 — Metadata governance

Metadata approval queue

Column override proposals submitted by non-admin editors land in user_data.business_name_overrides with status='pending_approval'. They are visible in Admin → Operations → Pending reviews. For editor instructions, see the Steward Guide.

Operational workflow

  1. Review the proposal: check the column identifier (catalog.schema.table.column), the current value, and the proposed business name / definition.
  2. Verify the proposed value is accurate, follows naming conventions, and is appropriate for the business glossary.
  3. Click Approve to publish. The row status changes to 'published', the change is enqueued for Databricks sync, and an audit event is logged.
  4. Click Reject to discard. The row is deleted from the overrides table. An audit event is still logged with the rejecting admin's email.
Approved changes sync automatically. Approved overrides are pushed to Databricks via the standard pending_sync queue within minutes. No additional action is required. See the Architecture Overview for more.

Bulk review via SQL (engineering)

SELECT table_full_name, column_name, business_name,
       definition, edited_by, updated_at
FROM user_data.business_name_overrides
WHERE status = 'pending_approval'
ORDER BY updated_at DESC;

Approval history

Every approval and rejection is recorded in user_data.audit_log with event_type='business_name_change' and the acting admin's email. Use the Audit log section in the Admin panel to filter and export.

§ 7 — Audit

Audit log access

All metadata edits, approvals, rejections, and comment activity are recorded in user_data.audit_log. The table is append-only and is mirrored to data_governance.dictionary_cache.audit_log via DR resync.

Via Admin dashboard

  1. Open Admin → Audit Logs tab.
  2. The change log shows the last 100 metadata events with actor, timestamp, object, and before/after values.
  3. The comment log shows the last 100 comment and reply events.
  4. Click Expand log to see the full history.

Direct SQL query (engineering)

-- Recent metadata changes by actor
SELECT event_type, object_type, object_name,
       old_value, new_value, actor_email, created_at
FROM user_data.audit_log
WHERE created_at > NOW() - INTERVAL 7 DAYS
ORDER BY created_at DESC
LIMIT 200;

§ 8 — Pipelines

Pipeline CRUD & troubleshooting

Register a new pipeline

  1. Open Admin → Operations → Pipelines section → New pipeline.
  2. Set the name (displayed in the Pipelines tab) and select the backend.
  3. Fill in backend-specific fields:
BackendRequired fields
DatabricksJob ID (from the Jobs UI URL)
Azure Data FactorySubscription ID, resource group, factory name, pipeline name
Azure DevOpsOrganisation, project name, pipeline ID

Delete a pipeline definition

  1. Open Admin → Operations → Pipelines.
  2. Click the delete icon (🗑) next to the pipeline. Confirm in the dialog.
  3. Any active run associated with this pipeline is cancelled automatically before deletion.

Service principal credentials

All three backends authenticate via MSAL client-credentials. Required environment variables:

PIPELINE_SP_TENANT_ID=<your-tenant-id>
PIPELINE_SP_CLIENT_ID=<service-principal-client-id>
PIPELINE_SP_CLIENT_SECRET=<service-principal-secret>
Secret rotation. When rotating PIPELINE_SP_CLIENT_SECRET, update the k8s secret and restart the app pod. The token cache is process-local and clears on restart. See secret-rotation runbook.

Stuck run (status never reaches terminal)

  1. Check the backend directly (Databricks Jobs UI, ADF Monitor, ADO Pipelines) to confirm the true run state.
  2. If the run is already complete in the backend but the Data Dictionary still shows it as running, clear the stale row: 
    DELETE FROM user_data.pipeline_runs
WHERE pipeline_id = '<id>';
  3. The Pipelines tab will show the pipeline as idle on the next page load.
§ 9 — Troubleshooting

Troubleshooting reference

User sees tables they should not have access to

Likely cause: stale group cache. Flush via Admin → Operations → Group cache → Flush group cache. If the problem persists after the user signs out and back in, verify the Unity Catalog grant has actually been revoked for their group.

User cannot see any tables after being added to a group

The cache TTL is 1 hour. Ask the user to sign out and sign back in (sign-out clears their personal cache). If they still see nothing, verify the Entra group was granted SELECT on the target tables in Unity Catalog.

Metadata changes are not reaching Databricks

  1. Check the sync queue in Admin → Operations. If rows are stuck in Failed, read the last_error and address the root cause.
  2. Check the heartbeat. If the worker is offline, see § 1 Sync queue — heartbeat stale.
  3. Confirm the service principal has MODIFY on the target tables in Unity Catalog.

The app returns "Error loading catalog" on the Search page

The SQL Warehouse is likely offline or the token has expired. Check DATABRICKS_HOST, DATABRICKS_HTTP_PATH, and DATABRICKS_TOKEN in the k8s secret. Verify the warehouse is running in the Databricks UI.

Admin panel shows no sync stats (all zeros)

DuckDB is unavailable (empty USER_DATA_PATH or the PVC is not mounted). Check the pod's volume mounts: kubectl describe pod <dd-app-pod>.

Health dashboard shows "No data"

The user's groups have no matching rows in permissions_cache. Run a nightly sync (python scripts/nightly_sync.py) or check that the permissions fetch step completed without errors in the last sync run.
